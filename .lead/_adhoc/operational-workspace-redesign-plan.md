# Operational Workspace — Phased Implementation Plan

## TL;DR
> **Summary**: Implement the resource-first operational home defined in the [design study](operational-workspace-design-study.md): nested observed containers, central safe update tasks, inline correlated work, automatic shared runtime observations, and honest running-image repository identities. Deliver additive data contracts before migrating navigation; no application implementation is authorized by writing this plan.
> **Estimated Effort**: Large

## Context
### Original Request
The UI feels cluttered, Overview provides too little actionable value, update tasks lack a central home, containers should be visible as children of stacks, and running syncs/pulls should remain visible and refresh automatically. Image digest is more useful than prominently displaying container ID. Produce the **design study first**, then a supporting phased plan; do not implement the app or a runnable prototype.

### Key Findings
- The study is the design authority for wireframes, interaction defaults, scope labels, edge states and navigation. It compares resource-first, task-inbox and multi-pane-explorer strategies and selects resource-first. It is conceptual, not user-validated research or live UI verification.
- `OverviewPage.vue` is passive; `StacksGrid.vue` has a flat table/cards; `App.vue` duplicates navigation and fixed active-work chrome. Routes, source comparison, logs, operation history and reviewed actions already exist and must survive.
- Global `/api/runtime` is already polled every 15 seconds while visible. `useStackContainers.ts` has a separate detail cache. Share observations, preserve stale data, and refresh on return/reconnect/terminal events rather than adding more independent polling.
- `store/stacks.ts` and `DeploymentProgress.vue` use singleton progress. Broadcaster cache keys are source/image/layer rather than run identity. Correct multi-run display requires backend changes, atomic reconnect snapshots and ordering, not a frontend-only map keyed by stack.
- Operation ancestry/versioning exists. Default history page contains 50 records; live work and parent-child grouping must not rely on that page. The existing history endpoint already supports stack/kind/status filters; related-child retrieval needs an explicit parent filter or authoritative snapshot ancestry.
- Runtime DTO has no digest. `docker.GetImageDigest` returns local `ImageInspect.ID`, not `RepoDigests`. SDK v28.5.2 already supports container/image inspection. Resolve immutable container image identity locally; remote registry freshness is a separate, deferred capability.
- Single-stack `retry`/`update` both pull then Compose up at a reviewed revision; no force recreation/prune. Global updater is sequential, skips failed stacks and prunes unused/dangling images host-wide. Manual Git check requests interruption and then applies configured reconciliation/removal policy. There is no selection batch, per-container update, general cancel, or dry-run refresh API.
- Vue 3, Pinia, PrimeVue 4, DM Sans and IBM Plex Mono already exist. Keep dependencies and backend lock/execution semantics. General console authentication is not present in the reviewed router; deployment's access boundary must be acknowledged rather than equating feature capabilities with authorization.

## Objectives
### Core Objective
Make one operational home answer what is running, what needs action, and what execution is in progress, with truthful identity/progress and explicit safety boundaries.

### Deliverables
- Approved study plus versioned design-level contract documentation and executable fixtures.
- Additive correlated live-work snapshots/events and active ancestry independent of retained-history pagination.
- Additive local running-image identity on scoped container observations, with safe unavailable/ambiguous behavior.
- Shared stale-aware runtime and keyed live-work stores; no singleton-derived inline bytes.
- One nested inventory with two real child previews per stack, bounded expansion, meaningful search and precise filter/action scope.
- Reusable scope-aware action controls, work summaries/pull detail and image inspector across home/detail/Operations/Repository.
- Incremental route/chrome migration with old deep-link/query compatibility.
- Unit, backend, browser, accessibility, large-inventory and real-Docker pull-lifecycle verification evidence.

### Definition of Done
- `/` leads to the operational Stacks workspace. Actual containers and active work are visible before navigation/disclosure; no redundant overview metrics or fixed work footer.
- Manual global update is reachable from home with explicit host-wide prune confirmation. Single-stack/approval controls retain reviewed revision and backend guards. No unsupported mutation control is introduced.
- Two same-image/layer runs do not collide; reconnect/restart cannot resurrect old bytes, duplicate workflow counts or infer successful completion from disappearance.
- Container identity is anchored to its exact immutable image ID; copied repository digest is full length and correctly labeled; “Registry freshness: Not checked” is explicit.
- Home and detail share automatic observations, preserve last-known data on failures, and never convert unknown to healthy/zero.
- Commands pass: `(cd frontend && bun run test && bun run build && bun run lint)`; `(cd backend && go test ./... && go test -race ./internal/desiredstate/... ./internal/operations/... ./internal/http/... ./internal/reconcile/... ./internal/scheduler/... ./internal/refresh/...)`; `(cd tests/e2e && bun run test:frontend)`; integration and real-browser lifecycle commands in Verification.
- Tech Lead reviews recorded before/after journey evidence and approves migration. No application changes occur before explicit user `/implement`.

### Guardrails (Must NOT)
- Do not ship a generic metrics dashboard, cosmetic-only reskin, second UI framework, mandatory newer Docker API or a new component-library dependency.
- Do not alter scheduler/reconciler sequencing, retry algorithm, policy/approval checks, prune scope or manual-refresh cancellation semantics as a side effect of UI work.
- Do not add selection/batch mutation, container update/restart/delete, cancellation/rollback, remote freshness, no-prune variants, desired-service inventory, multi-host/repo management or durable byte history in MVP.
- Do not show “outdated,” “latest,” “100% deployed,” “healthy,” or “completed” without evidence supporting that exact claim.
- Do not expose raw inspect/env/credentials, arbitrary host-resource inspection, or browser registry tokens. Capabilities must not substitute for server guards/access control.
- Do not break nested `/stacks/:path+`, old `/stack` redirects, query-backed tabs, log selection, source comparison, history URLs or filter return links.
- Do not consider fixture-based browser tests a substitute for real Docker pull/recreate/runtime-identity validation. Do not mark skipped Docker tests as passes.
